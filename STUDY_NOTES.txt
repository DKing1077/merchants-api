MERCHANTS API - SUPER CONCISE STUDY NOTES

1) ENTRY POINT FIRST
- app/main.py boots FastAPI, imports models, creates DB if missing, sets logging/metrics, then mounts all routers.
- Middleware: assigns X-Request-ID, times every request, logs request_complete/request_failed, and updates in-memory Prometheus-style metrics.
- Base routes:
  - GET / -> {"message": "API is running"}
  - GET /health -> checks DB with SELECT 1 and returns version
  - GET /metrics -> plain-text counters + latency histograms
- Router mount order:
  - /v1/payment_intents
  - /v1/refunds
  - /v1/webhooks
  - /v1/ledger
  - /v1/admin/risk
  - /v1/timestamps/payment_intents
  - /v1/api_keys
- End of boot: Base.metadata.create_all(bind=engine) creates tables from models.

2) SETTINGS / RUNTIME ASSUMPTIONS
- app.core.config is imported everywhere but the file is missing in this repo clone.
- The missing Settings object is expected to provide at least:
  - app_name
  - app_version
  - database_url
  - metrics_latency_buckets
  - merchant_velocity_window_seconds
  - merchant_velocity_limit
  - high_value_payment_threshold

3) DB SETUP
- app/db/database.py:
  - engine = create_engine(settings.database_url)
  - SessionLocal = sessionmaker(...)
  - Base = declarative_base()
  - get_db() yields a DB session per request.
  - create_database_if_missing() only does work for Postgres; it connects to the postgres admin DB and creates the target DB if absent.
- Alembic:
  - alembic/env.py loads Settings().database_url and migrates Base.metadata.
  - 2f837bbf0498_initial_schema.py creates the first payment_intents + refunds tables.
  - 4b9a66e4f7a1_feature_expansion.py adds merchant/risk/review fields and creates events, webhooks, ledger, and api_keys tables.

4) MODELS (SOURCE OF TRUTH)
- PaymentIntent:
  - id, merchant_id, amount, captured_amount, risk_score, currency, status
  - idempotency_key
  - is_flagged, review_status, review_reason
  - created_at, updated_at
  - computed total_refunded = sum of confirmed refunds
- Refunds:
  - id, merchant_id, payment_intent_id, amount, status
  - idempotency_key
  - is_flagged, review_status, review_reason
  - created_at, updated_at
- Event:
  - type, object_id, payload(JSONB), created_at
- WebhookEndpoint:
  - merchant_id, url, event_types(JSONB), secret, is_active
- WebhookDispatch:
  - event_id, webhook_endpoint_id, payload, status, next_retry_at
- WebhookDelivery:
  - webhook_dispatch_id, attempt_number, response_status/body, error_message, status, retry info
- LedgerAccount:
  - merchant_id, name, account_type, currency
- LedgerEntry:
  - entry_type, reference_id, description, entry_metadata
- LedgerPosting:
  - entry_id, account_id, amount, currency
- ApiKey:
  - key_hash, merchant_id, is_active, is_admin

5) AUTH / ACCESS RULES
- app/auth/dependencies.py:
  - Authorization header is treated as the raw API key.
  - API key is SHA-256 hashed and matched against api_keys.key_hash.
  - require_api_key -> 401 on missing/invalid key.
  - require_admin_api_key -> 403 unless is_admin=True.

6) ROUTES (EXTERNAL API SURFACE)
- Payments routes: app/api/routes/payments.py
  - GET /v1/payment_intents/ -> list merchant payment intents with filters: limit, starting_after, status, created_after/before, currency
  - POST /v1/payment_intents -> create payment intent; enforces merchant match; supports Idempotency-Key
  - GET /v1/payment_intents/admin/flagged -> admin list of flagged payment intents
  - GET /v1/payment_intents/transactions -> flattened transaction history across all merchant payment intents
  - GET /v1/payment_intents/{id}/transactions -> transaction history for one payment intent
  - GET /v1/payment_intents/{id} -> fetch one payment intent
  - POST /v1/payment_intents/admin/{id}/flag -> flag a payment intent with a reason
  - POST /v1/payment_intents/admin/{id}/review -> set review_status
  - POST /v1/payment_intents/{id}/confirm -> move to requires_capture
  - POST /v1/payment_intents/{id}/capture -> capture full or partial amount
  - POST /v1/payment_intents/{id}/cancel -> cancel remaining flow
- Refund routes: app/api/routes/refunds.py
  - GET /v1/refunds -> list refunds with limit, cursor, payment_intent_id, status
  - GET /v1/refunds/admin/flagged -> admin list of flagged refunds
  - POST /v1/refunds/payment_intents/{payment_intent_id}/refunds -> create refund; supports Idempotency-Key
  - GET /v1/refunds/{refund_id} -> fetch one refund
  - POST /v1/refunds/{refund_id}/flag -> flag refund
  - POST /v1/refunds/admin/{refund_id}/review -> set refund review_status
  - POST /v1/refunds/{refund_id}/confirm -> confirm refund
  - POST /v1/refunds/{refund_id}/decline -> decline refund
  - POST /v1/refunds/{refund_id}/cancel -> cancel refund
- Webhook routes: app/api/routes/webhooks.py
  - POST /v1/webhooks/endpoints -> create endpoint (HTTPS only)
  - GET /v1/webhooks/endpoints -> list merchant endpoints
  - PUT /v1/webhooks/endpoints/{id} -> update endpoint
  - DELETE /v1/webhooks/endpoints/{id} -> delete endpoint
  - GET /v1/webhooks/endpoints/{id}/deliveries -> all deliveries for one endpoint
  - GET /v1/webhooks/dispatches -> list dispatches; optional status filter
  - GET /v1/webhooks/dispatches/{id} -> dispatch + nested deliveries
  - GET /v1/webhooks/deliveries -> all merchant deliveries
  - POST /v1/webhooks/dispatches/process -> manually process pending dispatches
- Ledger routes: app/api/routes/ledger.py
  - POST /v1/ledger/accounts -> create ledger account for merchant
  - GET /v1/ledger/accounts -> list merchant accounts
  - POST /v1/ledger/entries -> create balanced double-entry record
  - GET /v1/ledger/accounts/{id}/balance -> account metadata + current balance
  - GET /v1/ledger/accounts/{id}/entries -> paginated entries with postings
  - GET /v1/ledger/merchant/{merchant_id}/balance_sheet -> grouped balances by account_type + currency
- Risk route: app/api/routes/risk.py
  - GET /v1/admin/risk/summary -> admin aggregate by merchant: total, flagged, approved, rejected, avg risk
- Timestamp routes: app/api/routes/timestamps.py
  - GET /v1/timestamps/payment_intents/{id}/created_at
  - GET /v1/timestamps/payment_intents/{id}/updated_at
- API key route: app/api/routes/api_keys.py
  - POST /v1/api_keys -> generates raw API key once, stores only SHA-256 hash

7) SERVICES (BUSINESS LOGIC)
- app/services/payment_service.py
  - create_payment_intent():
    - idempotency reuse by merchant + key
    - risk checks
    - high-value auto-flagging
    - creates payment_intent.created event
    - creates webhook dispatches
  - get/list helpers:
    - merchant-scoped reads
    - cursor pagination
  - list_payment_intent_transactions()/list_transactions():
    - synthesizes fake transaction timeline objects from payment intent state
  - flag/review:
    - updates manual review fields
  - confirm:
    - state guardrails
    - emits payment_intent.confirmed
  - capture:
    - supports partial capture
    - auto-creates Cash + Merchant Payable ledger accounts if missing
    - creates balanced ledger entry
    - emits payment_intent.partially_captured or payment_intent.succeeded
  - cancel:
    - disallows cancel after succeeded
    - emits payment_intent.canceled
- app/services/refunds_service.py
  - list/list_flagged -> cursor pagination
  - create_refund():
    - idempotency reuse
    - payment intent must exist
    - refund must be > 0
    - captured funds must exist
    - reserved + confirmed refunds cannot exceed captured_amount
    - emits refund.created
  - flag/review -> review workflow
  - confirm_refund():
    - only pending refunds
    - rejected refunds cannot confirm
    - confirmed refunds cannot exceed captured_amount
    - requires existing cash + merchant_payable ledger accounts
    - creates balanced refund ledger entry
    - emits refund.confirmed
  - decline_refund()/cancel_refund():
    - pending only
    - emits refund.declined / refund.canceled
- app/services/ledger_service.py
  - create_ledger_entry():
    - needs at least 2 postings
    - postings must sum to 0
    - reference_id + entry_type must be unique
  - get_account_balance_details() -> account metadata + sum(postings.amount)
  - list_account_entries() -> paginated ledger entries + postings
  - get_balance_sheet() -> grouped by account_type and currency
- app/services/risk_service.py
  - recent_payment_intent_count() -> merchant count in rolling window
  - enforce_velocity_limit() -> raises RiskRateLimitError when limit hit
  - calculate_risk_score():
    - base score
    - bumps for high amount, first merchant payment, and high recent velocity
    - caps at 100
- app/services/events.py
  - create_event() inserts event row and flushes it.
- app/services/dispatch.py
  - create_dispatches_for_event() finds active endpoints for merchant and queues matching event types.
- app/services/delivery.py
  - generate_webhook_signature() -> HMAC-SHA256 over compact sorted JSON
  - verify_webhook_signature() -> compare_digest
  - process_pending_dispatches():
    - picks pending dispatches whose retry time is due
    - POSTs JSON via httpx
    - sets X-Webhook-Signature
    - success = HTTP 2xx
    - retries up to 3 attempts with 5 minute delay
    - stores each attempt in webhook_deliveries
- app/services/timestamp_service.py
  - generic created_at / updated_at fetchers by table + id

8) SCHEMAS / VALIDATION
- Payment schemas:
  - statuses: requires_payment_method, requires_capture, succeeded, canceled
  - review statuses: pending_review, approved, rejected
  - merchant_id cannot be blank
  - currency must be exactly 3 letters and is normalized to lowercase
  - capture amount must be > 0 when provided
- Refund schemas:
  - statuses: pending, confirmed, declined, canceled
  - create refund amount must be > 0
- Webhook schemas:
  - webhook URL must be HTTPS
  - dispatch/detail payloads return nested delivery history
- Ledger schemas:
  - account types used by business logic: cash, merchant_payable
  - balance sheet groups by account_type + currency

9) IMPORTANT FEATURES TO REMEMBER
- API-key auth: raw key in Authorization header, DB stores only hash.
- Merchant isolation: most reads/writes are scoped to api_key.merchant_id.
- Idempotency:
  - payment creation
  - refund creation
- Risk:
  - velocity-rate limiting
  - high-value auto-flagging
  - admin review flow
- Event-driven behavior:
  - payment/refund state changes create Event rows
  - events fan out into webhook dispatches
- Ledger:
  - double-entry only
  - captures increase cash and decrease merchant payable
  - confirmed refunds reverse that movement
- Observability:
  - request ID header
  - structured request logs
  - Prometheus-style metrics

  - webhook signatures and retry timing work
