MERCHANTS API — IMPROVEMENTS & BUG FIXES
=========================================
Prepared as a guide for landing a backend engineer role (payments & risk).
The suggestions below are grouped into: bugs to fix first, then feature
additions that would genuinely impress an interviewer or hiring manager at
a payments company like Stripe.


════════════════════════════════════════════
SECTION 1: BUG FIXES
════════════════════════════════════════════

1. delivery.py — `hmac.new` should be `hmac.new` → actually `hmac.new` does
   not exist; the correct call is `hmac.new(...)` which IS the right name
   in Python's `hmac` module.  HOWEVER the argument order is wrong:
       WRONG:  hmac.new(key, msg, digestmod)
       RIGHT:  hmac.new(key, msg, digestmod)   ← actually the positional
   order is correct, but the secret is stored as a plain hex string and
   decoded with `.encode()`, which gives the raw UTF-8 bytes of the hex
   string rather than the 32-byte binary secret.  Fix:
       key = bytes.fromhex(endpoint.secret)
   This makes the HMAC actually use the binary secret that was generated
   with `secrets.token_hex(32)`.

2. test_payment_intents.py — `test_create_payment_intent_validation`
   sends amount=-1 and a two-character currency ("us") and asserts
   status_code == 201.  Negative amounts and invalid currencies should be
   rejected (422 from Pydantic or a 400 from the service layer).  The
   test currently documents broken validation.  Fix: add amount > 0 and
   currency length == 3 validators to `CreatePaymentIntentRequest` in
   payments_schemas.py, then update the test to assert 422.

3. refunds_service.py — `create_refund` checks `refund_amount > payment_intent.amount`
   but does NOT account for already-issued refunds on the same payment
   intent.  Two concurrent refunds each for half the amount would both
   pass the guard and together exceed the original charge.  Fix: sum
   existing non-cancelled refund amounts for that payment_intent_id before
   comparing.

4. payment_service.py — `pi_` IDs use a count-based approach:
       payment_intent_id = f"pi_{payment_intent_count + 1}"
   Under concurrent requests, two threads can read the same count before
   either commits, producing duplicate IDs.  Fix: switch to
   `"pi_" + str(uuid.uuid4())` (or a short-UUID variant), the same
   approach already used for Refunds, Events, etc.

5. refunds_service.py — `create_refund` raises `RefundNotFoundError` when
   the payment intent is not found, but the correct semantic is 404 on the
   payment intent, not on a refund.  Either create a separate
   `PaymentIntentNotFoundError` path or reuse the existing one from
   exceptions.py.

6. refunds_service.py — `confirm_refund` does not check that the payment
   intent itself has `status == succeeded` before reversing the ledger.
   A refund on a payment intent that was never captured would corrupt the
   ledger (cash account would go negative).  Fix: assert
   `payment_intent.status == "succeeded"` inside `confirm_refund`.

7. models.py / delivery.py — `datetime.utcnow()` is deprecated in Python
   3.12+.  Replace all occurrences with `datetime.now(timezone.utc)` and
   import `timezone` from the `datetime` module.


════════════════════════════════════════════
SECTION 2: FEATURE ADDITIONS
════════════════════════════════════════════

The following additions would meaningfully expand the API's production-
readiness and demonstrate backend engineering depth to a payments company.

─────────────────────────────────────────
A. INPUT VALIDATION & ERROR HANDLING
─────────────────────────────────────────

A1. Add Pydantic field validators to `CreatePaymentIntentRequest`:
    - amount must be > 0 (positive integer, no zero-value payments)
    - currency must be exactly 3 uppercase letters (ISO 4217)
    - merchant_id must not be blank/empty
    This is the first thing any reviewer at a payments company will look for.

A2. Add validators to `CreateRefundRequest`:
    - amount must be > 0
    - Return a structured JSON error body for all 4xx responses.  FastAPI
      does this automatically for Pydantic errors (422), but your custom
      exceptions produce inconsistent shapes.  Add a global exception
      handler in main.py to standardise the error envelope:
          {"error": {"code": "...", "message": "..."}}

A3. Validate webhook URLs: reject non-HTTPS URLs at registration time
    (important for security — HMAC secrets must not be sent over plain HTTP).

─────────────────────────────────────────
B. AUTHENTICATION & AUTHORISATION
─────────────────────────────────────────

B1. Add API key authentication.  Create an `ApiKey` model with fields:
    key_hash (SHA-256 of the raw key), merchant_id, is_active, created_at.
    Issue keys via a POST /v1/api_keys endpoint.  Add a FastAPI dependency
    `require_api_key` that reads the `Authorization: ****** header,
    hashes it, and looks it up.
    Store only the hash — never the plaintext key.

B2. Add merchant scoping: every route that lists resources (GET /v1/payment_intents,
    GET /v1/refunds, etc.) should filter by the authenticated merchant_id
    from the API key, not return all records across all merchants.  This is
    a significant security gap in the current implementation.

B3. Separate admin routes (/admin/*) behind a different authentication check
    (e.g. an internal service token or a role flag on the ApiKey model) so
    that regular merchant API keys cannot call flag/review endpoints.

─────────────────────────────────────────
C. PAGINATION & FILTERING
─────────────────────────────────────────

C1. All list endpoints (GET /v1/payment_intents, GET /v1/refunds, etc.)
    currently return every record.  Add cursor-based or offset pagination:
    - Query params: limit (default 20, max 100) and starting_after (ID cursor)
    - Response envelope: {"data": [...], "has_more": bool}
    This pattern mirrors Stripe's own API and is expected knowledge.

* you are here *
C2. Add filtering query params to the payment intents list:
    - status (e.g. ?status=requires_capture)
    - created_after / created_before (ISO-8601 timestamps)
    - currency

C3. Add filtering to the refunds list by payment_intent_id and status.

─────────────────────────────────────────
D. PARTIAL CAPTURES & PARTIAL REFUNDS
─────────────────────────────────────────

D1. Allow partial capture: accept an optional `amount` field on the
    POST /{id}/capture endpoint.  If supplied, capture only that amount
    (must be <= payment_intent.amount).  Store `captured_amount` on
    PaymentIntent.  A partial capture that succeeds leaves the uncaptured
    remainder available for cancellation.

D2. The refund service already supports partial amounts, but it does not
    track total refunded amount vs the captured amount.  Add a
    `total_refunded` derived field or a DB-computed column so you can
    enforce that sum(refunds) <= captured_amount.

─────────────────────────────────────────
E. RISK & FRAUD SIGNALS
─────────────────────────────────────────

E1. Auto-flag high-value payments: in `create_payment_intent`, if
    amount > a configurable threshold (e.g. 100_000 cents / £1,000),
    automatically set is_flagged=True and review_status=pending_review
    without requiring a manual flag call.

E2. Velocity check: before creating a payment intent, count how many
    payment intents the same merchant_id has created in the last 60 seconds.
    If the count exceeds a threshold (e.g. 10), raise a 429 Too Many
    Requests response.  Store this logic in a `risk_service.py` file.

E3. Add a `risk_score` integer field (0–100) to `PaymentIntent`.  Populate
    it on creation using simple heuristics (large amount, new merchant, etc.).
    This mirrors how real risk engines work and is a great talking point.

E4. Add a `GET /v1/admin/risk/summary` endpoint that returns counts of
    flagged vs approved vs rejected payment intents per merchant, and
    average risk scores.

─────────────────────────────────────────
F. WEBHOOK IMPROVEMENTS
─────────────────────────────────────────

F1. The current `process_pending_dispatches` fetches ALL pending dispatches
    on every call.  Add a `next_retry_at` filter so that dispatches waiting
    for a retry delay are not re-attempted too early:
        .filter(or_(
            WebhookDispatch.next_retry_at == None,
            WebhookDispatch.next_retry_at <= datetime.utcnow()
        ))

F2. Add a `GET /v1/webhooks/endpoints/{id}/deliveries` endpoint scoped to
    a single endpoint so merchants can debug their own webhook delivery
    history without seeing other merchants' data.

F3. Add webhook signature verification documentation / test: write a test
    that simulates receiving a webhook and verifying the `X-Webhook-Signature`
    header using the stored secret.  This proves the HMAC scheme works end-to-end.

F4. Expose a `GET /v1/webhooks/dispatches/{id}` endpoint to retrieve a
    single dispatch and its delivery attempts.  This is necessary for
    merchants to retry or debug failed webhooks.

─────────────────────────────────────────
G. LEDGER ENHANCEMENTS
─────────────────────────────────────────

G1. Add a `GET /v1/ledger/accounts/{id}/entries` endpoint that returns all
    ledger entries and their postings for a given account, sorted by
    created_at descending, with pagination.

G2. Add a `GET /v1/ledger/merchant/{merchant_id}/balance_sheet` endpoint
    that returns all account balances for a merchant, grouped by
    account_type and currency.  This gives a financial overview at a glance.

G3. The current `get_account_balance` returns a raw integer.  Wrap it in a
    response that also includes account metadata (name, account_type,
    currency, merchant_id) so callers do not need a separate lookup.

G4. Prevent double-posting: before committing a ledger entry, check that
    no entry with the same reference_id and entry_type already exists.
    Return a 409 Conflict if so.  This acts as an additional idempotency
    guard on the financial record.

─────────────────────────────────────────
H. OBSERVABILITY & OPERATIONS
─────────────────────────────────────────

H1. Add structured logging with a correlation ID.  Generate a UUID per
    request (via FastAPI middleware), attach it to every log line, and
    return it in the response as `X-Request-ID`.  This is table-stakes for
    debugging in production.

H2. Add a `GET /health` endpoint that checks DB connectivity and returns:
        {"status": "ok", "db": "connected", "version": "1.0.0"}
    Return 503 if the DB is unreachable.

H3. Add Prometheus-style metrics using `prometheus-fastapi-instrumentator`
    (or a simple counter dict behind a `GET /metrics` endpoint) to expose
    request counts, latency histograms, and error rates per route.

H4. Add request/response logging middleware that records method, path,
    status code, and latency for every request.

─────────────────────────────────────────
I. TESTING GAPS
─────────────────────────────────────────

I1. Add a test for idempotency: send two identical POST /v1/payment_intents
    requests with the same Idempotency-Key and assert that only one record
    is created and both responses are identical.

I2. Add a test for the full payment lifecycle:
    create → confirm → capture → refund → confirm refund
    and assert the ledger balance is zero (cash and payable net out).

I3. Add a test that verifies a high-amount payment intent is auto-flagged
    (once feature E1 is implemented).

I4. Add tests for the concurrent duplicate pi_ ID bug (B.4 above) using
    threading or asyncio to confirm the UUID-based fix eliminates collisions.

I5. The existing `test_create_payment_intent_validation` asserts 201 for
    invalid input — fix it to assert 422 after adding Pydantic validators
    (see A1).

─────────────────────────────────────────
J. CODE QUALITY
─────────────────────────────────────────

J1. Add a `requirements-dev.txt` (or `pyproject.toml`) that separates
    production dependencies from development tools (pytest, httpx, etc.).

J2. Add type hints to all service functions.  For example:
        def create_payment_intent(db: Session, amount: int, currency: str,
                                  merchant_id: str,
                                  idempotency_key: str | None = None) -> PaymentIntent:
    This improves IDE support and is standard at companies like Stripe.

J3. Move magic strings ("pending_review", "rejected", "cash", etc.) into
    Enum values or constants so they cannot silently diverge between the
    model, service, and schema layers.

J4. Add a pre-commit config (`.pre-commit-config.yaml`) running ruff (lint)
    and black (format) so code style is enforced automatically on every commit.

J5. Add a `Makefile` or `dev.sh` target for running the test suite with
    coverage:  `pytest --cov=app --cov-report=term-missing`

STRIPE ROLE RELEVANCE NOTES
════════════════════════════════════════════

The job listing emphasises:
  - "Designing and building APIs"     → sections C (pagination), D (partial capture), A (validation)
  - "Payments infrastructure"         → sections D, E (risk), G (ledger)
  - "Reliability and correctness"     → sections 1 (bugs), F (webhook retries), H (observability)
  - "Risk and fraud systems"          → section E is directly relevant

Priority order for maximum impact:
  1. Fix the bugs in Section 1 first — broken validation and ID collisions
     are red flags in a code review.
  2. Add authentication (B1, B2) — a public API with no auth is incomplete.
  3. Add pagination (C1) — interviewers always ask about this.
  4. Add risk features (E1, E2) — directly maps to the role description.
  5. Improve tests (I1–I5) — demonstrates engineering maturity.
