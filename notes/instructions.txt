Project roadmap notes

Current state:
- FastAPI app exists
- payment intents are implemented
- schemas/services/routes pattern exists
- PostgreSQL wiring exists
- payment intents are persisted
- basic error handling exists

Your goal now:
Build the rest of the app yourself using the same pattern:
model -> schema -> service -> routes -> tests

General rule for every new feature:
1. Add DB model if needed
2. Add schema(s)
3. Add service functions
4. Add route handlers
5. Register router in main.py if it is a new route group
6. Add tests
7. Manually test with curl

Suggested build order for the rest of the app:

1. Refunds
What to build:
- refund model
- refund schemas
- refund service
- refund routes
- refund tests

Routes:
- POST /v1/payment_intents/{payment_intent_id}/refunds
- GET /v1/refunds/
- GET /v1/refunds/{refund_id}

Notes:
- only allow refund on succeeded payment intents
- refund amount must be positive
- refund amount should not exceed payment amount
- keep first version simple

2. Add timestamps
What to build:
- created_at
- updated_at

Where:
- payment intents
- refunds
- later other models too

Notes:
- helps make the API feel more real
- useful for sorting and history

3. Better payment intent lifecycle
What to build:
- possibly add more statuses later
- maybe add capture if you want a richer payment flow

Possible routes:
- POST /v1/payment_intents/{payment_intent_id}/capture

Notes:
- only add this if you want more payment state modeling
- keep rules clear in service layer

4. Transaction history endpoint
What to build:
- endpoint to show all transactions related to a payment intent
- or endpoint to list activity across payment intents and refunds

Possible routes:
- GET /v1/payment_intents/{payment_intent_id}/transactions
- GET /v1/transactions/

Notes:
- can start simple
- even combining payment intents + refunds conceptually is okay at first

5. Idempotency support
What to build:
- allow POST requests to use an idempotency key
- prevent duplicate creates if the same request is retried

Notes:
- this is an important payment/backend concept
- do after core routes are solid

6. Alembic migrations
What to build:
- initialize Alembic
- create first migration
- stop relying on Base.metadata.create_all

Notes:
- this is how real DB schema changes should be managed
- do this before your schema grows too much

7. Improve tests
What to build:
- DB-backed test setup
- fixtures
- service-level tests
- route tests for every resource
- edge-case tests

Notes:
- this will help a lot once you add more features

8. Webhook events
What to build:
- event model or event records
- create events when important actions happen

Examples:
- payment_intent.succeeded
- payment_intent.canceled
- refund.succeeded

Possible routes:
- maybe internal only at first
- later webhook delivery endpoints/config

Notes:
- first just record events
- actual delivery can come after

9. Webhook delivery system
What to build:
- merchant webhook endpoint registration
- send event payloads to configured URLs
- retry on failure

Notes:
- this is more advanced
- okay to do later after event creation exists

10. Ledger / balance tracking
What to build:
- ledger entries
- balances derived from ledger postings

Notes:
- this is one of the hardest and most important later features
- do not rush it
- think carefully about immutable records

11. Suspicious transaction / review flow
What to build:
- flag transactions
- review status
- maybe simple admin review routes

Notes:
- optional but good advanced feature

12. Docker and local environment polish
What to build:
- Dockerfile
- docker-compose for app + postgres
- env file cleanup
- helper scripts

Notes:
- makes the project easier to run and share

13. Logging / observability
What to build:
- request logging
- error logging
- maybe structured logs

Notes:
- important for production style apps
- can be added once main features exist

Suggested milestone order:
1. refunds
2. timestamps
3. improve tests
4. alembic migrations
5. transaction history
6. idempotency
7. webhook events
8. webhook delivery
9. ledger/balances
10. docker/logging/polish

How to approach each feature:
- start small
- keep rules in services
- keep HTTP logic in routes
- keep schemas focused on validation and response shape
- test happy path first
- then test failure cases

When in doubt:
- copy the payment intent pattern
- follow the same folder structure
- keep version 1 simple, then improve later
